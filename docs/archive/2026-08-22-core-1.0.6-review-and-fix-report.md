# DeepSeek Harness Desktop 核心版 1.0.6 审查与修复报告

审查日期：2026-08-22

审查范围：Electron 主进程、官方 DSH Runtime 启动链、插件搜索/安装子进程、桌面 IPC、社群与旧扩展残留、依赖策略、Windows NSIS 打包、自动更新元数据和 GitHub Actions。

## 结论

本轮已修复用户在 DSH 搜索或安装插件时出现 Windows 黑色终端窗口的问题，并生成可用于发布和自动升级的 `1.0.6` 安装包。核心单元测试、包内容校验和打包启动冒烟测试均通过。

旧插件集合、皮肤、QQ Bot、社群窗口、星标提示、任务看板、营销网站及其构建/发布工作流已删除。安装包体积和全新安装固定开销已降低。

当前剩余的主要发布风险是安装包没有 Authenticode 代码签名，以及官方 Windows Web Surface 暂时不能在 Electron renderer sandbox 中正常导航。这两项没有被隐藏为“已完成”。

## 审查发现

### 高：官方通用子进程缺少 Windows 隐藏窗口参数，导致插件搜索仍弹黑框 - 已修复

证据：旧修复只覆盖 `@deepseek-ai/dsh` 插件转发和 `@deepseek-ai/dsh-web-app` 浏览器启动；插件搜索还会经过 `@deepseek-ai/dsh-subprocess-local` 的通用 `spawn()`。该入口原来只设置 `detached`，没有设置 `windowsHide`。

修复：新增 `patches/@deepseek-ai__dsh-subprocess-local@0.1.1-rc.2.patch`，在 Windows 为通用子进程设置 `windowsHide: true`；通过 `pnpm-workspace.yaml` 固定应用该补丁；新增三路径回归测试，分别覆盖插件转发、浏览器启动和通用子进程。

验证路径：`apps/dsh-desktop/test/dsh-plugin-window.test.mjs`。

验收结果：三项窗口隐藏测试通过，完整测试 222/222 通过。

### 高：已发布版本号无法承载修复，现有用户不能自动升级 - 已修复

证据：修复开始时源码与已发布标签都为 `1.0.5`。继续复用同一版本会造成同版本不同二进制，electron-updater 也不会把它识别为新版本。

修复：根包和桌面包统一提升为 `1.0.6`；重新生成 `latest.yml`、`.blockmap` 和 NSIS 安装包。

验收结果：`latest.yml` 显示 `version: 1.0.6`，文件名为 `DeepSeek-Harness-Desktop-Setup-1.0.6-x64.exe`。

### 中：仓库仍包含大量已删除功能源码和失效 CI - 已修复

证据：原仓库仍跟踪旧 `gallery/`、`website/`、`.dsh/`、插件/皮肤脚本、社区质量矩阵、旧 npm 发布和网页部署工作流；本地还残留未进入工作区的 `packages/` 与 `shared/`。

修复：删除上述源码、资源、文档和工作流；根 `package.json` 收敛为 Desktop 核心命令；CI 只执行 Desktop 核心测试和 E2E；README、隐私政策、安全说明、贡献说明和更新日志按当前核心版重写。

验收结果：工作区只包含 `apps/*`，GitHub Actions 只保留 `desktop-ci.yml` 和 `desktop-release.yml` 两条核心链路。

### 中：安装包包含 55 个 Electron locale，并在全新安装时执行升级扫描 - 已修复

证据：修改前安装包为 124,493,165 字节，解包目录为 454,836,893 字节、10,287 个文件；缺失旧安装目录时，升级清理 PowerShell 单测耗时约 2.0 秒。

修复：打包配置只保留 `en-US`、`zh-CN`；NSIS 在 `$INSTDIR` 不存在主程序和 `app.asar` 时直接跳过旧版本进程扫描，覆盖升级和卸载仍执行完整检查。

验收结果：1.0.6 安装包为 116,131,901 字节，减少 8,361,264 字节，约 6.72%；解包目录为 407,025,402 字节，减少约 47.81 MB；locale 从 55 个降为 2 个；全新安装避免约 2 秒固定扫描开销。

### 中：Windows renderer sandbox 与当前官方 Web Surface 不兼容 - 未解决，已验证边界

证据：将主窗口改为 `sandbox: true` 后，Runtime 在约 1.76 秒进入 ready，但打包冒烟测试收到 `ERR_FAILED (-2)`，180 秒内页面不能加载。撤回 Windows sandbox 后，同一构建在约 2.23 秒加载到 renderer，冒烟测试通过。

当前处理：Windows 继续使用 `sandbox: false`，但保留 `contextIsolation: true`、`nodeIntegration: false`、严格导航策略、默认拒绝权限和主表面 IPC 校验。macOS/Linux 保持 sandbox。

后续建议：单独建立上游兼容任务，定位 Electron sandbox 下 loopback 导航失败原因；在打包冒烟测试通过前不要再次强行开启。

### 中：Windows 安装包没有 Authenticode 签名 - 未解决

证据：`Get-AuthenticodeSignature` 对 1.0.6 安装包返回 `NotSigned`。

影响：Windows SmartScreen 可能显示未知发布者；用户无法通过发布者证书验证来源。SHA-256 只能验证下载后文件一致性，不能替代发布者身份。

后续建议：购买或配置可信代码签名证书，在 GitHub Actions 中通过受保护 Secret 完成签名，并在发布后验证 `Valid`、时间戳和证书链。

### 低：依赖供应链保护与刚发布的官方 RC 批次冲突 - 已修复

证据：24 小时 `minimumReleaseAge` 会阻止刚发布约 16 小时的 186 个官方 rc.2 包；pnpm 不支持“命名空间通配符加精确版本”的例外表达式。

修复：改为不设例外的全局 12 小时发布时间保护。当前 796 个锁文件条目通过策略校验，所有桌面依赖继续精确锁定并由 frozen lockfile 安装。

### 低：构建依赖仍有维护告警 - 待跟踪

证据：`pnpm install` 报告 `koffi@3.1.4` 和 6 个传递依赖已废弃，并存在 peer dependency 告警。

建议：不要在 1.0.6 中无验证地升级 Runtime 依赖。后续建立独立依赖升级分支，执行 222 项测试、E2E、打包校验和真实安装测试后再合并。

## 发布前最后检查

1. 在一台没有安装过本软件的 Windows 电脑上实测全新安装、首次启动和卸载。
2. 在已安装 1.0.4 或 1.0.5 的电脑上覆盖升级到 1.0.6，确认原应用退出、数据保留和更新完成。
3. 在 DSH 中实际搜索并安装一个可信测试插件，使用任务管理器或 Process Explorer 确认没有可见 Windows Terminal、PowerShell 或 CMD 窗口。
4. 发布 GitHub Release 后，确认 Release 同时包含 EXE、blockmap、`latest.yml` 和 SHA256SUMS。
5. 从旧版执行“检查更新”，确认读取到 1.0.6，而不是本地直接运行安装包得出的假阳性。
